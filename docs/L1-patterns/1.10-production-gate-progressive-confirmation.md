# Pattern 1.10 — Production Gate and Progressive Confirmation

Green stack tests are local evidence. A fix still needs a gate outside the agent that decides whether it may
proceed, and a staged rollout that confirms it in production. Read it when an agent's fix is about to leave CI for
production.

## Problem

Verification on a developer machine does not show how a change behaves under production traffic. If the repair agent
can also decide that production confirmed its fix, it grades its own work a second time.

## Solution

**The agent may act up to the production gate and cannot pass it** ([AN-27](../references/sources.md)).

**The gate is deterministic code outside the agent.** It is a pipeline step or deploy hook. Its inputs are the
evidence bundle ([Pattern 1.9](1.9-repair-loop-frozen-oracle.md)) and the classes ([risk
model](1.8-reversibility-blast-radius.md#risk-model)). It returns one of three results, and the most severe finding
wins, as in [Pattern 2.3](../L2-behavioral-guardrails.md#composing-checks):

- `auto`: every check passed and the class is within the `auto` ceiling. The change goes on as a pull request with
  the evidence bundle, and the grant decides who merges it: below A4 a person; at A4 and A5 nobody for the classes
  in the [gate rule table](1.11-repair-budget-circuit-breaker-stop.md#grants-and-repair-capability), a person for
  the rest.
- `human`: stop and send the bundle to a named person, who decides whether the change goes on at all.
- `block`: reject, with the reason.

Only `auto` changes proceed. Whoever merges them, they reach production only through progressive delivery:

1. **Roll out behind a flag or a canary** to a small share of traffic.
2. **Confirm under a rule declared in advance.** For example: zero occurrences of the incident fingerprint across at
   least N requests on the cohort, and an error rate no worse than the control. Code evaluates the rule. The agent
   does not.
3. **Require a minimum sample.** No errors on a path with no traffic is not evidence.
4. **Roll back automatically** when the rule fails or the window ends without enough traffic. Rehearse the rollback
   on a schedule ([AN-27](../references/sources.md)).
5. **Prefer flag-off to revert** when many changes land in quick succession, because a revert can undo unrelated
   work ([PO-28](../references/sources.md)).

Production confirmation is statistical, so it uses graded evidence, allowed only under the pre-declared rule and
only for gates on reversible actions ([Pattern
4.1](../L4-standards-measurement.md#pattern-41--evidence-based-claims)).

## In Practice

The production mode of the health endpoint ([Pattern 1.1](1.1-stack-tests.md#health-endpoint-test-mode)) gives the
confirmation step the same signals the stack tests used: status, per-dependency state and version.

The gate is a pure function of a typed evidence bundle, so it can be evaluated like any other decision layer
([Pattern 4.6](../L4-standards-measurement.md#pattern-46--context-eval)). Score it exactly, not with partial credit,
and report pass^k over repeated runs: a scenario passes at pass^k only when all k runs pass, and the suite score is
the share of scenarios that pass.

A simplified form of `gate` in `examples/repair-loop/typescript/src/gate.ts`. Every check adds a finding, and the
most severe decision wins (`block` over `human` over `auto`):

```typescript
const findings: { decision: Decision; reason: string }[] = [];
const add = (decision: Decision, reason: string) => findings.push({ decision, reason });

if (reproduction.frozenSha256 !== reproduction.currentSha256) add('block', 'reproduction test changed after it was frozen');
if (!reproduction.greenOnCandidate) add('block', 'reproduction is not green on the candidate');
if (bundle.antimask.length > 0) add('human', 'anti-masking hits: treated as a mitigation');
if (exceeds(bundle.classification, policy.autoCeiling)) add('human', 'class is above the ceiling');
// decision = the most severe finding, or 'auto' when there are none
// merge = 'unattended' only within policy.unattendedCeiling[grant] (A4 and A5), otherwise 'person'
```

In [`examples/repair-loop/`](../../examples/repair-loop/README.md) the workflow holds A3, so every `auto` result is
a pull request that a person merges; the gate eval also scores the merge at A4 and A5. The example simulates the
confirmation step: after an `auto` result it treats the pull request as merged, replays the incident 50 times
against the candidate stack and counts the fingerprint in the app logs, under a pre-declared rule. It does not prove
production behavior.

Each repair that uses a flag leaves a flag behind. Give flags a removal rule ([Pattern
0.8](../L0-foundation.md#pattern-08--aggressive-cleanup)).

## Anti-Pattern

- **The agent summarizes the canary.** The agent has then become the gate.
- **A confirmation window with no minimum sample.**
- **A gate that advises.** A gate that warns and lets the change pass is not a gate ([Pattern
  2.3](../L2-behavioral-guardrails.md#pattern-23--hook-automation)).
- **Graded evidence on an irreversible action.** Statistical confirmation cannot undo a sent payment.
