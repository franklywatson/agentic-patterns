# Pattern 1.6 — Test Integrity Rules

Every test passes or fails explicitly: no conditional assertions, swallowed errors or soft asserts, each held by a lint
rule or CI step. Adopt it first if you adopt one L1 pattern: an agent trusts a green suite.

## Problem

A test with an escape hatch passes when it should fail: an early return skips a failing test, a try-catch wraps an
assertion "to see what happens," or optional chaining turns a missing value into a passing check. Agents declare
success on a green suite, so a test that can pass silently removes the signal the whole loop depends on.

## Solution

**Test integrity rules** remove the escape hatches: every test must either pass or fail explicitly, and every
assertion runs unconditionally and fails fast. The first failing assertion ends the test. Collecting several
failures and reporting them at the end (a soft assertion) is forbidden for the same reason as a swallowed error: it
changes what a failure means. The assertion layers in [Pattern 1.2](1.2-full-loop-assertions.md) are an ordering for
diagnosis under this rule, not an exception to it.

## In Practice

Six forbidden patterns, each with its correct form:

| # | Forbidden | Why it can pass silently | Correct |
|---|-----------|--------------------------|---------|
| 1 | `if (response) { expect(response.status).toBe(200); }` | An undefined `response` runs no assertion | `expect(response).toBeDefined(); expect(response.status).toBe(200);` |
| 2 | `try { await op(); } catch (e) { console.log(e); }` | The test passes when `op` fails | `await expect(op()).resolves.not.toThrow();`, or rethrow with context |
| 3 | `expect(res?.error).toBeUndefined();` | An undefined `res` (a failed request) makes the optional chain `undefined` and the assertion pass | `expect(res).toBeDefined(); expect(res.error).toBeUndefined();` |
| 4 | `if (!user) return; expect(user.email).toContain('@');` | A null `user` ends the test with no assertion | `expect(user).toBeDefined(); expect(user.email).toContain('@');` |
| 5 | `try { expect(actual).toBe(expected); } catch (e) {}` | The failed assertion is swallowed | `expect(actual).toBe(expected);` |
| 6 | `softAssert(response.status === 200); softAssert(response.data.id);` | Execution continues after a failure and the report comes last | `expect(response.status).toBe(200); expect(response.data.id).toBeDefined();` |

Separate assertions on existence and on properties, so the failure names the missing thing.

### Enforcement

Each check below can fire on a concrete violation. A prose rule does not block anything; a lint rule or a CI step
does.

- **Jest and Vitest lint**: [`eslint-plugin-jest`](https://github.com/jest-community/eslint-plugin-jest) with
  `jest/no-conditional-expect` (patterns 1, 2, 5), `jest/no-conditional-in-test` (patterns 1 and 4) and
  `jest/expect-expect` (a test with no assertion). For pattern 3, add an ESLint `no-restricted-syntax` selector
  `CallExpression[callee.name='expect'] > ChainExpression`. For empty catch blocks, enable ESLint `no-empty`.
- **No-assertion guard**: call `expect.hasAssertions()` in a `beforeEach` in the Jest setup file, so a test that
  runs zero assertions fails.
- **pytest**: set `filterwarnings = error` (or run with `-W error`), `--strict-markers` and `strict_xfail = true`
  ([pytest reference](https://docs.pytest.org/en/stable/reference/reference.html)), so warnings, unknown markers and
  unexpectedly passing `xfail` tests fail the run. No standard pytest plugin catches conditional assertions; review
  `assert` inside `if` or `try` in the diff.
- **Skips**: a CI step that greps the diff for `test.skip`, `it.skip`, `pytest.mark.skip` and `pytest.mark.xfail` and
  fails when the line carries no issue reference.
- **Mutation check**: run a mutation tester ([Stryker](https://stryker-mutator.io/) for JavaScript and TypeScript,
  [`mutmut`](https://github.com/boxed/mutmut) for Python) on the modules a change touches. A surviving mutant is a
  code change no test caught: the measurable form of a test that cannot fail.

## Anti-Pattern

**Don't** leave "TODO: re-enable" comments that skip tests. A test that is legitimately blocked moves to a separate
suite or uses `test.skip` or `@pytest.mark.skip`, and each skip names an issue and a review date.

**Don't** use test hooks (`beforeEach`, `beforeAll`) to set up conditions that silently skip tests. Assertions belong
in test bodies.
