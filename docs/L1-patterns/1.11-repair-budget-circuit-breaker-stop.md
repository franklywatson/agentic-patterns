# Pattern 1.11 — Repair Budget, Circuit Breaker and Stop Authority

Limit how often a repair workflow may act, lower its grant when its repairs fail, and give a named person a tested
stop. This pattern holds the gate rule table: what the repair gate allows at each grant.

## Problem

Automatic repair at production volume oscillates: repair, regress, revert, repair again. Zero-defect tolerance turns every alert into a trigger. A healthy agent can still take harmful actions ([PO-14](../references/sources.md)). Without limits and a stop, the loop runs until a human notices.

## Solution

Four controls, all enforced by code outside the agent.

**Attempt budget.** Each incident fingerprint gets a fixed number of automatic attempts, for example one. After that, a human takes over. A per-service daily budget and global limits on spend and turns bound the total.

**Cooldown.** After any rollback, the same fingerprint is not retried until a set time has passed.

**Circuit breaker on outcomes.** The breaker trips on the recurrence rate: the same fingerprint returning within N days of a repair marked confirmed. A revert rate (repairs rolled back) is a second possible trip signal; the example does not implement it. When the threshold is crossed, the workflow's grant drops one step automatically, for example from A4 to A3, then to A2 (A1 for read-only diagnosis). Write the lowered grant as the autonomy demotion override ([Pattern A.3](../earned-autonomy.md#pattern-a3--promotion-demotion-and-the-cap-gate)) so the autonomy hook enforces it; the example keeps it in the breaker state only. Raising it again is a recorded decision by a named person. Use two thresholds. The trip level is worse than the reset level, so the grant does not flap.

**Stop authority.** A named person or role can stop the workflow with one switch. The switch is tested on a schedule. A named role approves restore after any incident the agent caused. The stop belongs to an on-call owner, not a committee.

### Grants and repair capability

The grants are defined in [Earned Autonomy](../earned-autonomy.md#the-grants); the classes and review tiers are the
[risk model](1.8-reversibility-blast-radius.md#risk-model). This table is the rule the gate in [Pattern
1.10](1.10-production-gate-progressive-confirmation.md) applies: which candidates may get `auto`, and which `auto`
changes merge with no person.

| Grant | Repair capability | Merges unattended |
|-------|-------------------|-------------------|
| A1, A2 | The gate returns `human` for every candidate. | Nothing |
| A3 | The agent drafts a reproduction and a fix pull request from an incident record. The gate returns `auto` up to R2 at B1, and a person merges with the evidence bundle. | Nothing |
| A4 | A3, plus first-pass diagnosis on every incident, with a canary, budgets, a tested stop and a register entry. | R0 and R1 at B0 |
| A5 | A4, plus a grant that rises or falls on repair outcomes (recurrences, reverts) and a retirement decision at each review. | R0 and R1 at B0; R2 at B0 on named paths only |
| Any grant | R3, R4, B2 and B3 candidates get `human`. | Never R3, R4 or above B0 |

Unattended repair of R3 and R4 changes is not supported at any grant, for three reasons. A data-forward or external action cannot be undone by a rollback, so the confirmation window protects nothing. No source cited here shows unattended code repair of incidents; Google describes agent-driven mitigation under rate limits and a stop button, not repair ([PO-28](../references/sources.md)). And no case cited here names who answers for an agent's harmful action. The reference domain, a trading bot, is mostly R4: on-chain transactions cannot be reversed.

## In Practice

The breaker is a small state machine over the repair history, with its thresholds in the repair policy config.

```python
def next_grant(grant: str, recurrences: int, policy: Policy) -> str:
    if recurrences >= policy.trip_recurrences:
        return lower(grant)
    return grant  # raising a grant is a recorded human decision, never automatic
```

[`examples/repair-loop/`](../../examples/repair-loop/README.md) implements the recurrence trip and the stop switch ([stack test 05](../../examples/repair-loop/typescript/tests/stack/05-breaker-trips.stack.test.ts)): a simulated recurrence after a confirmed repair drops the grant, and the stop switch is pulled and checked. The policy sets `tripRecurrences` and `resetCleanRepairs` in `shared/config/repair-policy.json`, and encodes the table above as `autoCeiling`, `unattendedCeiling` and `unattendedR2Paths` (the named paths: route handlers). The gate code refuses unattended merge above R2 or B0 whatever the policy says.

Recurrence detection depends on a stable fingerprint. A stack trace changes with the fix, so fingerprint on the failing journey and the error class, not on line numbers. Each workflow has a register entry: owner, sponsor, permitted classes, budgets, stop switch, date of the last stop test, and a review date.

## Anti-Pattern

- **A breaker that only alerts.** It must change the grant.
- **A stop nobody may pull.** Name the person and test the switch.
- **Automatic restore.** The agent never raises its own grant.
- **Counting repairs as success.** See the repair metrics in [Pattern 4.4](../L4-standards-measurement.md#pattern-44--agentic-development-metrics).
