# Pattern 1.1 — Stack Tests

Run the whole application in Docker and check one user journey per test through the API, with no mocks for services
you own. Read this first in L1: the other patterns refine these tests, and A4 requires one per journey ([Why Stack
Tests Earn Autonomy](../earned-autonomy.md#why-stack-tests-earn-autonomy)).

## Problem

Partial-stack integration tests that mock some components and run others describe a system that does not exist: they
pass and production fails. Unit tests are fast and test one module's behavior through its public interface, not
how the system behaves end to end. E2E tests are comprehensive but slow and brittle. The one narrow exception is a
focused integration test of a single external dependency ([Pattern
1.5](1.5-real-dependencies.md#focused-integration-tests-for-external-dependencies)). The team needs a test level that
gives confidence in real behavior and still runs on a developer machine.

## Solution

**Stack tests** run the complete Docker stack (app, databases, caches, queues) and verify behavior through the API
only. No internal mocks, no backend shortcuts. The test treats the system as a black box: it starts the stack, waits
for readiness, makes API calls and asserts on observable effects.

Each stack test models one **atomic user journey**, a single complete interaction from the user's perspective. Not
"does the order service work?" but "a user places an order, pays, and sees their balance update." Stack tests
validate the design intent set during context harvesting ([L1 overview](../L1-feedback-loops.md)).

- **Scope**: the entire system in real containers, plus external dependencies as far as a sandbox allows
- **Verification**: API only; tests act like external clients
- **Isolation**: full isolation between runs ([Pattern 1.4](1.4-container-isolation.md))
- **Mock policy**: zero mocks for owned services
- **Diagnosticity**: high once isolation holds; in this project's experience failures point at real defects more often than at the test,
  though brittle tests and infrastructure faults still produce test-artifact failures
- **Runs on a developer machine**: Docker only, so a person or an agent gets the same result locally

## In Practice

A stack test generates a compose file with dynamic ports, runs `docker compose up -d`, waits for health checks,
drives the journeys over HTTP, asserts on primary and second-order effects ([Pattern 1.2](1.2-full-loop-assertions.md))
and runs `docker compose down -v`. Leaving that orchestration to the agent is brittle: each session re-derives it, and
the first port collision or stale volume sends the agent debugging infrastructure instead of the application.

**Turn brittle agent-side orchestration into deterministic tooling.** The first time agent-managed Docker operations
cause a problem, write the tooling that removes it: a toolkit that wraps container lifecycle, port allocation, health
polling, authentication and cleanup behind calls such as `await stack.initialize(...)` and `await stack.cleanup()`.
The [reference project](../references/reference-telegram-trading-bot-case-study.md) grew its `StackTestUtils` this way
over many sessions. The runnable equivalent is `StackTestUtils` in
[`examples/stack-test/typescript/tests/config/stack-utils.ts`](../../examples/stack-test/typescript/tests/config/stack-utils.ts):
initialize, request, wait for ready, get logs, clean up. Its `cleanup()` rethrows a failed `docker compose down`, and unit tests cover it. A toolkit may seed fixture data for the bootstrap step below;
it does not give tests direct database access for assertions ([Pattern 1.2](1.2-full-loop-assertions.md#anti-pattern)).

Each test is one journey, ordered by dependency ([Pattern 1.3](1.3-sequential-design.md)):

```text
tests/stack/
  01-app-startup.stack.test.ts         # system comes online and reports healthy
  02-bootstrap-test-data.stack.test.ts # fixture data loaded
  03-authentication.stack.test.ts      # user registers, logs in, receives a token
  04-user-crud.stack.test.ts           # user creates, reads, updates, deletes a resource
  05-checkout-complete.stack.test.ts   # user adds items, checks out, payment succeeds
  06-refund-and-reconciliation.stack.test.ts  # user requests a refund, balance updates
```

"Does authentication work?" tests a component. "A user registers, logs in and receives a valid token" tests a journey,
and journeys catch component-interaction bugs that component tests cannot.

### Stack tooling is production code

The toolkit (port allocators, compose generators, container managers, health pollers, auth helpers) is application
code that serves testing, and every stack result depends on it. A port allocator with a race condition produces
intermittent failures that look like application bugs, and an auth helper that swallows errors sends the agent to
debug the wrong layer.

- **Unit test the utilities**, including exhausted port ranges, duplicate ports and a failed `docker compose down`
  (the example's `stack-utils.test.ts` covers these). Add concurrent allocation and permission errors for your own toolkit.
- **Throw on failure.** A utility that returns null or logs silently hides what the agent needs to diagnose.
- **Review it like application code**, with no lower standard, and treat flaky infrastructure as a defect
  ([Pattern 2.5](../L2-behavioral-guardrails.md#pattern-25--zero-defect-tolerance)).
- **Split it when it grows.** A multi-thousand-line utility class is a god file
  ([Pattern 0.1](../L0-foundation.md#pattern-01--deep-modules)). The reference project's single `StackTestUtils`
  class runs to several thousand lines and breaks this rule.

## Comparison: Test Types

| Dimension | Unit Tests | Focused Integration Tests | Stack Tests | E2E Tests |
|-----------|------------|---------------------------|-------------|-----------|
| Scope | Single function or class | Adapter code + one real external dependency | Full system + external dependencies as far as sandboxes allow | Full system + external dependencies |
| Proves | One module's contract ([Pattern 0.5](../L0-foundation.md#pattern-05--unit-tests-as-contract)) | The adapter handles the dependency's real behavior | A user journey works through the full stack | A critical path works in a shared environment |
| Mocks | Everything | None (real API) | None | None |
| Diagnosticity | One module's logic; nothing on integration | High | High | Low (timing, flakiness) |
| Runs locally | Always | Usually (testnet or sandbox) | Must (Docker only) | Often needs cloud or staging |

## Beyond API Testing

For web applications the same pattern applies with browser automation such as Playwright: start the full stack and
drive journeys through the UI. Real system, real dependencies, no mocks; only the entry point changes.

## Anti-Pattern

**Don't** write "integration tests" that start a few services and mock others. They test the mocks. Test at the unit
level, use a focused integration test for one external dependency, or test at the stack level.

**Don't** run the full stack suite on every code change. Use unit tests for rapid iteration and run the single stack
test for the journey being built ([Pattern 1.3](1.3-sequential-design.md)). Run the full suite before committing.

## Caveats and Scope

Stack-first development is easiest on greenfield projects. Large existing systems (dozens of microservices,
specialized hardware, components that resist containerization) may not fit one stack. Adopt incrementally: pick the
highest-value subsystem, extract it behind a clean API boundary, stack-test that boundary and keep it there. Coverage
ratchets forward one boundary at a time.

## Stack Test Brittleness and Reconciliation

The deeper a journey reaches, the more reasons it has to fail, and a journey covering authentication, ordering,
payment, fulfillment and audit logging is brittle by construction. The remedy is to reconcile the test design, not
remove coverage. Ask the agent to scan the domain's stack tests and propose a simpler structure with the same
coverage: de-duplicate assertions that verify the same side effect, group journeys around coherent concerns, and
reduce the surface each test depends on so a failure points to one subsystem.

Reconcile a domain's stack tests when a new test overlaps an existing one, for example a new incident reproduction
([Pattern 1.7](1.7-incident-to-stack-test.md)).

## Health Endpoint Test Mode

The startup test checks more than "is the server running?", because a configured dependency can still be
unhealthy. `GET /health?mode=test` adds service-level diagnostics:

```json
{
  "status": "healthy",
  "services": {
    "postgres": { "connected": true, "latency_ms": 3 },
    "redis": { "connected": true, "latency_ms": 1 },
    "message_queue": { "connected": true, "pending_jobs": 0 }
  },
  "version": "2.4.1",
  "env": "test"
}
```

The JSON is illustrative. The apps in `examples/stack-test/` return `"status": "ok"` and fewer checks.

A `/test/db-health` or `/test/queue-health` endpoint is an anti-pattern: it adds test-only code to production, leaks
infrastructure details and needs maintenance beside the real endpoints. One health endpoint serves both the simple
production check and the detailed test-time diagnostics.

### Production mode

Without the test parameter the endpoint returns only what an operator and a repair loop need:

```json
{
  "status": "degraded",
  "dependencies": { "postgres": "connected", "redis": "timeout" },
  "version": "2.4.1"
}
```

- `status` is one of `healthy`, `degraded` or `unhealthy`.
- `dependencies` gives one state per dependency.
- `version` is the deployed commit or release, so a confirmation step compares like with like
  ([Pattern 1.10](1.10-production-gate-progressive-confirmation.md)).

Latency figures and counts stay in test mode. An incident record copies the dependency states from this response
([Pattern 1.7](1.7-incident-to-stack-test.md)). The example apps implement test mode. The repair-loop apps return the test-mode shape for `?mode=prod`, latency
included, which this section recommends against in production; their README explains why.

## Test Fixture Data Bootstrap

A user cannot place an order against an empty catalog. **Bootstrapping** loads fixture data after the startup test and
before domain tests (typically `02-bootstrap-test-data.stack.test.ts`): products, pre-configured users, reference
data and system settings.

- Use the internal service APIs that user-facing or admin functions use, not synthetic test-only endpoints.
- Direct database seeding is acceptable for bootstrapping if it goes through the application's service layer and
  data access code, not raw SQL that bypasses validation, hooks or business logic.
- Each bootstrap test creates one category of fixture data.
- Domain tests assume every bootstrap test passed, so a bootstrap failure makes all later results meaningless.
