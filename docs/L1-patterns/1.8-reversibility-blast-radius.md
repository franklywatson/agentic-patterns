# Pattern 1.8 — Reversibility and Blast-Radius Classes

Classify every proposed change from its diff, in code, before any human sees it. Two scales: how reversible the
change is (R0 to R4) and how far it reaches (B0 to B3). Read it before letting any change merge with no person, or
when deciding who reviews a change.

## Problem

"May the agent do this unattended?" is usually answered per request by a person. At volume, people approve almost
everything: one vendor measured 93% of permission prompts approved ([SG-9](../references/sources.md)). Approval at
that rate is not a control. Few actions need it: one vendor's classification of about a million public-API tool
calls found 0.8% that appear irreversible ([MC-20](../references/sources.md)).

## Solution

A classifier reads the diff and its target and returns a reversibility class and a blast-radius class. The rules are
data, not prose. When the classifier cannot decide, it fails closed: an unclassified change is R4 at B3, high tier.

| Class | Meaning | Example |
|-------|---------|---------|
| R0 Inert | No runtime effect | A test, a log field, a doc |
| R1 Flag-reversible | New path behind a flag that defaults off; undo is one config write | A guarded code path |
| R2 Deploy-reversible | Revert and redeploy restores the prior state; no data written in a new shape | A pure logic fix |
| R3 Data-forward | Writes data the old version cannot read, or migrates a schema | A migration, a backfill |
| R4 External or irreversible | Money moved, message sent, third-party state changed, data deleted | A refund, an email, a chain transaction |

| Class | Reach | How it is measured |
|-------|-------|--------------------|
| B0 | One journey, internal | Which stack tests touch the changed files |
| B1 | One service, all users | Files owned by one service |
| B2 | A cross-service contract | A change to a public interface (the deep-module seam, [Pattern 0.1](../L0-foundation.md#pattern-01--deep-modules)) |
| B3 | Money, auth, PII or audit | Paths on an owner-maintained list |

### Risk Model

This table is the risk model. The class sets the review tier, whose approvals the [README
table](../earned-autonomy.md#how-the-scales-fit-together) states; the [grant](../earned-autonomy.md#the-grants) decides
whether a change merges with no person; below A4 a person always merges.

| Class | Review tier | Merges with no person | Enforcement points |
|-------|-------------|-----------------------|--------------------|
| R0-R1 at B0 | Low | At A4 and A5 | Required checks; the autonomy hook blocks merging below A4 ([A.6](../earned-autonomy.md#pattern-a6--enforcement-through-hooks)); outside the repair loop, the path check below; the gate, canary and rollback ([1.10](1.10-production-gate-progressive-confirmation.md)); budget, breaker and tested stop ([1.11](1.11-repair-budget-circuit-breaker-stop.md)) |
| R2 at B0 | Low | At A5, on named paths only | As above, plus the named paths in the repair policy |
| R0-R2 at B1 or B2 | Medium | Never | At B1 the repair gate can return `auto` and a person merges; at B2 it returns `human`. The workflow's permitted paths ([A.1](../earned-autonomy.md#pattern-a1--autonomy-register)) |
| R3 or R4 at any reach, or any class at B3 | High | Never | A code-owner review on high-tier paths; protected branches and scoped tokens ([2.11](../L2-behavioral-guardrails.md#pattern-211--agent-identity-and-delegation)); a downstream control |

Owner-listed paths and CI workflow files always need a person ([AN-29](../references/sources.md)). Each team lists
its high-tier paths in its instruction file ([Pattern
0.4](../L0-foundation.md#pattern-04--agent-instruction-file-as-project-constitution)); this repository's list is in
[AGENTS.md](../../AGENTS.md#high-tier-paths). Locked files ([Pattern
A.6](../earned-autonomy.md#pattern-a6--enforcement-through-hooks)) are permission and hook surfaces and high tier.
Instruction and tool-configuration files (`CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `GEMINI.md` and `.mcp.json` at any depth, and anything under a `.claude/` folder except `.claude/settings*.json` and `.claude/hooks/**`) are behavior surfaces and medium tier, edited in ordinary pull
requests. The repair-loop policy classes them R0 at B1 (and `.claude/settings*.json` and `.claude/hooks/**` at any depth R4/B3), so the gate can return `auto` and a person merges
([example](../../examples/repair-loop/README.md#gate-rules)).

**Unattended merge and required review.** One required approval on every pull request makes A4 impossible. This
branch ruleset lets a low-tier A4 change merge on checks ([GitHub
rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging)):

1. Require pull requests and status checks. Set required approvals to 1, or to 0 once an A4 workflow runs.
2. Turn on "Require review from Code Owners", which applies only to a pull request that changes a file with a code
   owner. List only high-tier paths in CODEOWNERS, with no catch-all `*` line.
3. On an organization repository, add a "Required reviewers" team rule with 2 approvals on the high-tier paths. On a
   personal repository the second approval is a convention no rule enforces.
4. Turn on "Require approval of the most recent reviewable push" and "Dismiss stale pull request approvals".

Keep the agent's identity out of CODEOWNERS and the reviewer team. With 0 required approvals, no platform rule
covers medium-tier changes, low-tier changes below A4, or human pull requests; the person who merges holds their
approval. A ruleset sees paths, not classes, and outside the repair loop nothing classifies a change: the hook's
`merge-limits` rule reads the session's working tree, not the pull request. A person or a required CI check (a
`.github/workflows` job you add) compares the pull request's files with the low-tier paths.

## In Practice

In [`examples/repair-loop/`](../../examples/repair-loop/README.md) the rules are data in
`shared/config/reversibility.json`. Each changed file takes its first matching glob, content rules can raise the
class, and the diff takes the highest class across its files. An excerpt:

```json
{
  "unknown": { "reversibility": "R4", "blast": "B3" },
  "paths": [
    { "glob": "app/src/routes/**", "reversibility": "R2", "blast": "B0" },
    { "glob": ".github/**", "reversibility": "R4", "blast": "B3" }
  ],
  "content": [
    { "name": "external-effect", "pattern": "\\b(sendMail|smtplib)\\b|\\bfetch\\(", "reversibility": "R4" }
  ]
}
```

Score the classifier exactly with the context-eval method ([Pattern
4.6](../L4-standards-measurement.md#pattern-46--context-eval)): a half-correct class on an irreversible action is a
miss.

Read the diff, not the description. A "pure logic" change that alters how amounts are rounded is R4 in a payments
system.

## Anti-Pattern

- **Classifying from the commit message** or the agent's own summary.
- **Failing open.** An unknown change treated as low risk.
- **An unmaintained owner list.** The B3 class is only as good as the list, and classification drifts as code moves.
- **A human approval for every change.** Decide about classes of change, not each instance.
