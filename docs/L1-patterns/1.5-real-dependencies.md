# Pattern 1.5 — Real Dependencies in E2E/Integration and Stack Tests

Stack and E2E tests run real databases, caches and owned services; unit tests may mock. Read it when deciding what a
test may mock.

## Problem

Mock system components in end-to-end tests and the tests check the mocks, not the system. Mocks return perfect data,
never time out and never throw unexpected errors, while real databases have latency, real APIs return errors and
real caches miss.

This rule covers **stack tests and E2E/integration tests only**, the tests that verify system behavior through the
API. Unit tests validate module contracts in isolation, and mocks are appropriate and encouraged there
([Pattern 0.5](../L0-foundation.md#pattern-05--unit-tests-as-contract)).

## Solution

Stack and E2E/integration tests use real PostgreSQL, real Redis, real RabbitMQ and real HTTP calls to other
services. If you own it, run it. If you can run it in Docker, run it in Docker. If you cannot, that is a deployment
dependency, not a testing concern. The only acceptable mocks are external services you do not control and that offer
no sandbox or test mode.

## In Practice

What to mock, by test level (the test levels are compared in [Pattern 1.1](1.1-stack-tests.md#comparison-test-types)):

| Component | Mock in stack/E2E? | Mock in unit? | Reason |
|-----------|--------------------|---------------|--------|
| PostgreSQL, MySQL, MongoDB | No | Yes | Stack: run in Docker. Unit: mock for isolation. |
| Redis, Memcached, RabbitMQ, Kafka | No | Yes | Same |
| Internal microservices | No | Yes | Stack: run the full stack. Unit: mock to test module logic. |
| External APIs with a sandbox (Stripe, Plaid) | No | Yes | Stack: use the sandbox. |
| External APIs without a sandbox | Yes | Yes | No test environment exists at any level. |
| Time (for expiry) | Only through a time-skewing library, not a stubbed clock in the app | Yes | Stack: time-skewing libraries. Unit: mock freely. |

In a stack test, call the real sandbox:

```typescript
const stripe = new Stripe(process.env.STRIPE_TEST_KEY!);
const payment = await stripe.paymentIntents.create({
  amount: 1000,
  currency: 'usd',
  payment_method: 'pm_card_visa', // Stripe test payment method
  confirm: true,
  automatic_payment_methods: { enabled: true, allow_redirects: 'never' },
});
expect(payment.status).toBe('succeeded');
```

Replacing the client with `{ paymentIntents: { create: () => ({ id: 'pi_mock', status: 'succeeded' }) } }` in a stack
test passes and tells you nothing about the real integration. The same stub is correct in a unit test, where it
isolates the payment logic and lets the test force declined cards and network errors:

```typescript
const mockStripe = {
  paymentIntents: { create: jest.fn().mockResolvedValue({ id: 'pi_test', status: 'succeeded' }) },
};
```

## Focused Integration Tests for External Dependencies

Some external dependencies have contracts too nuanced to cover through the full stack: payment providers with dozens
of error codes and idempotency rules, blockchain RPCs with nonce and gas edge cases. One full system start per error
code is impractical, and unit tests with mocks test your assumptions.

A **focused integration test** exercises one external dependency's real API (testnet or sandbox) with exhaustive
edge-case coverage, without the full stack: your adapter code plus the real service. No mocks.

Use one for an external dependency with a complex contract or many error states, or whose documentation does not
capture its behavior. Do not use one for services you own (those belong in stack tests), as a replacement for stack
tests (it verifies adapter code, not user journeys) or with mocks (use a unit test for that).

```typescript
describe('Stripe payment adapter, edge cases', () => {
  const adapter = new StripePaymentAdapter(process.env.STRIPE_TEST_KEY!);

  it('maps a declined card to a non-retryable failure', async () => {
    const result = await adapter.charge({ card: '4000000000000002', amount: 1000, currency: 'usd' });
    expect(result.status).toBe('failed');
    expect(result.errorCode).toBe('card_declined');
    expect(result.retryable).toBe(false);
  });
});
```

The test checks what the real sandbox does, not what its documentation says. The three levels answer different
questions: unit tests check module logic, focused integration tests check how an adapter handles one dependency's
real behavior, and stack tests check that the system delivers a journey.

## Fault Injection Is Not a Mock

Many incidents are a dependency misbehaving: a Redis timeout, a slow database, a dropped connection. Reproducing them
needs the dependency to fail on cue.

**Network-level fault injection in front of a real dependency is not a mock.** A TCP proxy sits between the
application and the real Redis or PostgreSQL container and delays, truncates or drops traffic. The application still
talks to the real service through its real client. **Replacing the client is a mock**: a stub that throws a timeout
tests your assumption about the failure, not the failure.

```typescript
// Allowed in a stack test: real Redis, real client, a proxy that adds 5 s of latency
const proxy = await startFaultProxy({ upstream: redisAddress, latencyMs: 5000 });
const app = await stack.start({ redisUrl: proxy.url });
const response = await app.post('/orders', orderBody);
expect(response.status).toBe(503);
```

`startFaultProxy` and `stack.start` are placeholders for your own helpers. The repair-loop example in
[`examples/repair-loop/`](../../examples/repair-loop/README.md) does not demonstrate this carve-out; it has no
incident that reproduces a dependency timeout.

## Anti-Pattern

**Don't** mock databases or sandboxed external services (Stripe, Plaid, Twilio) in stack tests "because they are slow." In this project's experience, PostgreSQL in Docker adds seconds to startup, and sandboxes catch integration bugs mocks hide.

**Don't** mock for "determinism" in stack tests. Real systems are non-deterministic, and you want tests to fail when
race conditions exist, not hide them behind perfect mocks.

**Don't** avoid mocks in unit tests out of misplaced consistency, or dismiss focused integration tests as partial
stack tests: their purpose is exhaustive coverage of one dependency's contract.
