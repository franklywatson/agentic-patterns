# Pattern 1.7 — Incident-to-Stack-Test

Every incident in code you own ends with a reproduction stack test. The test fails on the production commit and passes on the fix. No repair is proposed until the reproduction is red. This pattern needs no autonomy: a human-run team can adopt it at any grant.

## Problem

An incident is diagnosed and patched, but the system gains no test that would have caught it. The next agent session meets the same failure from zero. A prose postmortem or a written learning does not execute, so it cannot fail when the bug returns.

## Solution

Treat the reproduction as the artifact of record. The postmortem links to it.

1. **Record the incident in a fixed schema.** Fingerprint, journey, PII-free request, observed versus expected behavior, and dependency states taken from the health endpoint ([Pattern 1.1](1.1-stack-tests.md#health-endpoint-test-mode)). The same schema is the contract between the application and the operations side ([FAQ](../cross-cutting/faq.md#what-passes-between-the-application-and-operations)).
2. **Render a stack test from the record.** Use the stack toolkit described in [Pattern 1.1](1.1-stack-tests.md), never production data.
3. **Run it on the current production commit.** It must fail, and it must fail for the reason the record states.
4. **Place it in the sequential suite** at the position of the subsystem it exercises ([Pattern 1.3](1.3-sequential-design.md)).
5. **Freeze it** before any fix is written ([Pattern 1.9](1.9-repair-loop-frozen-oracle.md)).

Two rules follow:

- **"Cannot reproduce" is a valid, final outcome.** It routes to a human. It is not a license to patch blind. Scale, data shape and concurrency incidents often do not reproduce on a developer machine, so expect a share of incidents to end here.
- **Agent configuration incidents become eval cases.** If the cause is a prompt, a skill, a model or a permission, the artifact is a case in the context-eval suite ([Pattern 4.6](../L4-standards-measurement.md#pattern-46--context-eval)), not a stack test. Start that suite from 20 to 50 real failures ([AN-16](../references/sources.md)).

## In Practice

An incident record, trimmed from `shared/incidents/INC-001.json` in [`examples/repair-loop/`](../../examples/repair-loop/README.md):

```json
{
  "id": "INC-001",
  "journey": "user-lookup",
  "errorClass": "pg:22P02",
  "fingerprint": "92e2a8020bd5",
  "request": { "method": "GET", "path": "/users/undefined" },
  "observed": { "status": 500 },
  "expected": { "status": 404, "body": { "error": "User not found" } },
  "dependencies": { "postgres": { "connected": true }, "redis": { "connected": true } },
  "replayPaths": ["/users/undefined", "/users/null", "/users/0"]
}
```

The reproduction asserts the invariant, not the payload: any malformed user id returns 404, not 500. An assertion on the one reported id passes a fix that guards only that id and lets the class of bug survive, which is why the record lists `replayPaths`.

The example renders a reproduction from this record, shows it red on the base commit and green after the fix patch ([stack test 02](../../examples/repair-loop/typescript/tests/stack/02-repair-INC-001.stack.test.ts)).

Keep the suite lean. Each incident adds a journey, so reconcile it with existing tests when it overlaps ([Pattern 1.1](1.1-stack-tests.md#stack-test-brittleness-and-reconciliation)).

## Anti-Pattern

- **Patching first.** A fix with no red reproduction proves nothing.
- **Over-fitted reproductions.** Asserting the exact payload instead of the invariant.
- **Approximating production data** until the test no longer reproduces the failure.
- **Prose-only learnings.** A note in a solutions folder that nothing runs.
