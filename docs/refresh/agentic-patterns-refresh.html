agentic-patterns · critical review and evolution proposal

Agentic Patterns Refresh

The repository was reviewed against the research baseline and the Anthropic guidance companion, by five reviewers with different lenses. The verification core holds up well and should become the centre of the library. Most of the optimisation layer has aged. Security, ownership and measurement are missing, and those three set the ceiling on how much autonomy any adopter can safely grant. This page proposes how the library grows into two goals: software that earns its own autonomy, and software that repairs itself.

1 · Verdict

What holds, what has aged, what is missing

Holds, and matters more now

  • Stack tests, full-loop assertions and test integrity (1.1, 1.2, 1.6). They turn "the agent says it worked" into a signal a machine can trust, which is what earns delegation (finding 2; AN-2, AN-3).
  • "Prose is suggestion; enforcement is deterministic" (L2). The research now backs it with independent sources (SC-8, OM-7, OM-18, SG-11, SG-16).
  • Evidence-based claims (4.1) and context eval (4.6). Both match the field's best practice on self-report and task banks (IS-6, MV-9).

Has aged

  • Command routing, intent classification and environment detection (3.1–3.3, 3.8). Current harnesses ship native tools that do this.
  • TOON (3.7). Its worked example is arithmetically wrong.
  • Token-saving figures (60–90%). They are unsourced, and the docs disagree with each other.
  • A mandatory five-phase skill chain with a blocking phase tracker (2.2, 2.7). This ceremony compensated for models that skipped planning or verification.
  • The 150-line CLAUDE.md rule, while CLAUDE.md @-imports every doc.

Missing

  • Containment: sandbox, egress, credentials and agent identity.
  • Ownership: agent register, author of record, a tested stop and retirement.
  • Measuring value against a baseline.
  • Any notion of per-workflow autonomy, or of production beyond the development loop. The FAQ scopes production out.

The central reframe. L0–L4 is a capability stack. It says whether letting go is safe. It does not say how much a given workflow is allowed to let go, on what evidence, or how that grant is withdrawn. The research's defensible top is exactly that missing piece: "the ability to raise autonomy for a named workflow when evidence supports it, show that evidence, and lower it again" (baseline 3.7).

So keep the layers. Add an orthogonal autonomy axis, gated by the cap rule. Fill the three capping dimensions the library ignores. Self-repair then becomes one family of workflows on that axis, rather than a new level on top of the pyramid.

Method. Five reviewers each read the full repository and both research pages:

  1. evidence held the repo to its own "every claim verifiable" rule.
  2. autonomy mapped the pyramid onto the 5 × 7 curve.
  3. repair extended the closed loop into production.
  4. governance covered security, ownership and people.
  5. adopter red-teamed the repo as a staff engineer in Nov 2026 working with Claude 5-generation models.

Their findings converged far more than they conflicted. Where they disagreed, section 10 says so. Lens tags beside a finding show who raised it.

What this means

The library produces teams that are good at verified, attended delegation. It does not give them the scaffolding to earn unattended delegation. Its strongest dimensions, shared context and operating model, are exactly the two that do not set the cap. The repo never tells readers this.

Where the pyramid misleads

Pattern 4.4 maps maturity stages one-to-one onto L0–L4 and puts "Autonomous: end-to-end delivery" at the top. That is a single sequential ladder with a volume-based top, the two flaws the baseline names (3.3, 3.7). It treats token efficiency (L3) as "self-optimizing", and places measurement last when the curve needs a baseline before autonomy rises.

4 · Goal A

Software that ladders itself up to autonomy

The repo already has most of the A3 machinery: blocking hooks, constitutional rules, the enforcement pipeline, CI guardrails and context eval as a task bank. What it lacks is a binding between that machinery and an explicit, revocable grant. The A-series supplies it. The common per-agent trust-tier design (promotion on consecutive successes) is the seed; the comparison table below shows what changes. autonomy

A.1Autonomy register

Partial

A committed, schema-validated .autonomy.yaml lists every agent workflow. Interactive sessions count as a workflow. Each entry records owner, sponsor, grant, identity, permitted and forbidden actions, risk class, limits, stop mechanism with its last-tested date, review date and stop rule. It is protected by CODEOWNERS and is never writable by an agent.

A.2Evidence ledger

Partial

An append-only record per run, written only by CI and by jobs that observe source control afterwards, never by the agent. It captures check results, reverts, rework within 14 days and escaped defects. A harness_hash covers model, CLAUDE.md, skills and hooks; changing it is a release.

A.3Promotion, demotion and the cap gate

Thin

Promotion moves one level at a time, through a human-approved PR with ledger evidence that uses lower confidence bounds. Demotion is automatic and immediate, with hysteresis and a cooldown. autonomy check is a required CI check and has no exception field.

A.4Self-placement census

Partial

autonomy census probes artefacts for presence and practice: last changed, run by CI, exercised in the ledger. It writes a profile with one level per dimension. Unknown cells count as C2, so missing evidence lowers the cap instead of being ignored.

A.5Tested stop

Thin

Every A4+ workflow gets a monthly drill. It triggers the stop against a canary run, asserts the halt and token revocation, restores the workflow and records the date. A failed drill demotes the workflow.

A.6Enforcement through hooks

StrongThin

SessionStart computes the effective level. PreToolUse blocks anything outside the grant, including any agent write to .autonomy*, CODEOWNERS or CI config. PostToolUse writes an audit line. Context eval gains an autonomy suite that tests the gate itself.

Strong on the mechanism; thin on outcomes.

A.7Portfolio review

Thin

At each review date a job opens an issue with the ledger trend, cost per merged outcome against the baseline, and the stop rule evaluated. The owner records keep, promote, demote or retire. Retirement revokes the identity.

5 · Goal B

Self-repairing software

The repo closes a development-time loop. Self-repair closes a production-time loop. The only evidenced top of the curve is unattended change "because verification is mechanical and the action reversible", as in Spotify's 2.5 million auto-merged maintenance PRs (MC-21). The repo supplies the mechanical half and none of the reversible half. No unattended incident repair was found in either research document; only maintenance. repair

The repair loop: what exists (solid) and what is missing (dashed)

  1. detect
  2. diagnose (1.3 ladder)
  3. reproduce from incident
  4. propose fix
  5. verify (1.1, 1.2, 1.6)
  6. classify risk
  7. production gate
  8. progressive confirm
  9. learn (2.8, prose only)
  10. stop / roll back

The health endpoint's test mode (1.1) is a ready-made detection probe, but it is only defined for test runs.

These are proposed as an L1 sub-family, "Closing the loop in production". Production repair is the same closed loop with a different trigger and a wider confirm step. It is blocked by L4 maturity, not stacked on top of it.

1.7Incident-to-stack-test: reproduce before repair

StrongPartial

Every incident in owned code ends with a reproduction stack test. It is red on the pre-fix commit, green on the fix, and placed in the sequential suite. No repair is proposed until the reproduction is red. "Cannot reproduce" routes to a human. Incidents in agent configuration become eval cases instead.

Ship this first. It is useful at A3 with no autonomy at all, and it turns compound engineering from prose into executable regression tests.

1.8Reversibility and blast-radius classes

PartialTaxonomy new

Each proposed action is classified deterministically from the diff, before any human sees it. Reversibility: R0 inert, R1 flag-reversible, R2 deploy-reversible, R3 data-forward, R4 irreversible or external. Blast radius: B0 single journey, B1 one service, B2 cross-service contract, B3 money, auth, PII or audit. Unknown is treated as the highest class, so the classifier fails closed.

1.9Repair loop with a frozen oracle

StrongOracle separation new

The reproduction test is frozen, as a protected path, before the fix is written. The fix may not touch existing tests. An anti-masking scan applies 1.6's six forbidden patterns to production diffs: swallowed exceptions, new retries, widened timeouts, lowered thresholds. A hit reclassifies the change as a mitigation and routes it to a human.

The repair reviewer calls separating the oracle from the repairer the most original contribution the repo could make.

1.10Production gate and progressive confirmation

PartialThin

"The agent may act up to the production gate and cannot pass it" (AN-27). The gate is deterministic code outside the agent that returns auto, human or block. Auto changes go out behind a flag or canary, with a pre-declared confirmation rule and a minimum sample size. Rollback is automatic on failure, and rehearsed.

1.11Repair budget, circuit breaker and stop authority

PartialNone found in practice

Each incident fingerprint gets an attempt budget, with a cooldown after any rollback. If repair-revert or recurrence rates rise, the workflow drops one grant automatically; restoring it is a recorded human decision. A named on-call role holds a tested stop. Anthropic names this breaker as not yet built (AN-29).

1.12Self-healing tests are not self-healing systems

Definitional

Tests never heal themselves; a test that rewrites its own assertions is a soft assertion. A test the loop wants to change means the spec changed, which is a design decision. Systems heal at three depths: runtime recovery, mitigation and repair. Only repair produces a learning artefact. Recovery that repeats without a repair ticket is a masked defect.

GrantDefensible repair capability
A3The agent drafts a reproduction and fix as a PR from an incident record. A human merges. An evidence bundle is required.
A4First-pass diagnosis on every incident. R0–R1 / B0 repairs go through the gate with a canary, budgets, a tested stop and a register entry.
A5Grants move on revert and recurrence evidence, and workflows are retired. R2 repairs run unattended for named classes only.

Where self-repair collides with the repo's own constitution
  • Zero-defect plus automatic action flaps. In production, zero-defect should govern what must be addressed (triaged, fingerprinted, owned), not what is auto-repaired.
  • Automatic repair tends to mask. The fastest way to make an error disappear is to catch it. Without the 1.9 anti-masking scan, a repair loop converts defects into silent defects.
  • Evidence is binary; production confirmation is statistical. Accept graded evidence under a pre-declared decision rule decided by code, and say so. Keep it out of gates for irreversible actions.
  • "Real dependencies" blocks the commonest reproduction. Most incidents are a dependency misbehaving. Add a carve-out: network-level fault injection in front of a real dependency is not a mock; replacing the client is.
  • Doc freshness. A repair that changes behaviour must update docs in the same change, so a code-only repair loop breaks rule 4 by construction.
  • Approval fatigue. "A human approves every auto-repair PR" is the worst design: polished evidence bundles get less scrutiny (IS-3), and 93% of prompts are approved (SG-9). Humans decide about risk classes, not each instance.
6 · The prerequisite track

Containment, ownership and people

Both goals are blocked by the same three capping dimensions. This track lifts them, and the adoption guide should check it before any team moves from attended to unattended work. governanceautonomyadopter

Proposed replacement for the L2 thesis. Prose is guidance. Hooks are deterministic policy within the harness. Containment and credentials are the boundary. Put each rule at the lowest layer that can hold it:

  • What must never happen is prevented by the sandbox, credential scope or downstream authorisation.
  • What must always happen runs as a hook and a required CI check.
  • Prompts and skills carry everything else.

A hook is inside the agent's operating environment, so it is not a security boundary. An allowed bash is a general-purpose computer, and hook configuration is often a file the agent can edit.

Vendor neutrality

  • Write each pattern against a neutral contract. Then add short bindings for Claude Code, one other harness, and "no harness: CI only".
  • Make AGENTS.md the shared source, with CLAUDE.md importing it. Claude Code reads only CLAUDE.md when both exist (AN-8).
  • Disclose the author's relationship to rig, the most-cited reference implementation, as the Anthropic guidance companion discloses its own lean.

A lesson from compound engineering

2.8 lets agent-written learnings flow into future prompts without review, so one bad session can poison later ones (IS-13). A masked repair recorded as a "solution" would be inherited by every later session. Promote a learning only after review, and only after the confirmation window and recurrence check pass. Pair capture with pruning.

7 · Prune and re-baseline

Apply the library's own cleanup rule to itself

The repo has not changed since 18 April 2026. That makes it an instance of the RAMP finding it should warn about: committed AI configuration that is present but never maintained (MC-11). Anthropic reports removing over 80% of Claude Code's system prompt for the Claude 5 generation with no eval loss (AN-7). The library needs the same pass, and a pattern for adopters to repeat it. adopterevidence

NewPrune and re-baseline context

Partial

Give every context artefact (instruction file, skill, hook, rule) an owner, a reviewed date and an expiry. Keep a fixed task bank of 10–30 tasks against a pinned model. On each model upgrade, or quarterly, delete first: run the bank without the artefact, and add it back only if a task regresses, recording which task justified it. Classify each rule as guidance, which is prunable prose, or invariant, which lives in a hook, deny rule or CI. Track how recently each artefact changed, not whether it exists.
